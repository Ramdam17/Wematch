# Wematch — Audit Report (2026-07-15)

Consolidated findings from a full project audit: environment/method review, architecture
deep-review, and a 15-domain automated health check (~141 findings: 24 CRITICAL,
48 HIGH, 47 MEDIUM, 30 LOW). This document keeps the CRITICAL/HIGH picture; it is the
factual base for `Docs/plans/plan-20260715-reboot.md`.

**Scope:** 128 Swift files (~9,600 lines) across Wematch (iPhone), WematchWatch Watch App,
WematchShared. All 14 planned sprints (0–13) marked done as of 2026-02-15; repo untouched
since 2026-02-17 (including an uncommitted real bugfix, see E3).

---

## A. Environment & Method

- **A1 (CRITICAL)** No project-level `.claude/` — no settings, skills, hooks, or permission
  allowlist specific to Wematch. The rich user-level tooling is not wired to the project.
- **A2 (CRITICAL)** `Docs/CLAUDE.md` is never auto-loaded (Claude Code reads root `CLAUDE.md`).
  The best document of the project is disconnected — and outdated (describes "Sprint 0 start" state).
- **A3 (CRITICAL)** `WematchTests` has **no Xcode target** (`grep WematchTests project.pbxproj` → 0).
  The 6 test files were never compiled or run. Sprint "run unit tests" steps were structurally
  impossible. Real coverage: 0 %.
- **A4 (HIGH)** No CI, no SwiftLint/SwiftFormat, no automated build verification.
- **A5 (HIGH)** Firebase security rules are nowhere in the repo (no `firebase.json`, no `*.rules`).
  Access control for live heart-rate data is unverifiable.
- **A6 (MEDIUM)** Repo hygiene: `firebase-debug.log` (57 KB) untracked at root; `.serena/`
  partially ignored; uncommitted work since Feb 17.
- **A7 (context)** No Figma / visual source of truth: design spec is prose + hex values in
  markdown. Contrast failures (see D2) are the direct consequence.
- **A8 (positive)** `CAHIER_DES_CHARGES.md` and `SPRINTS.md` are genuinely good — the plan
  was sound; the verification loops (tests, design, field testing) never closed.

## B. Security & Privacy — verdict: NOT READY

- **B1 (CRITICAL)** All CloudKit repositories use `publicCloudDatabase` with client-side
  filtering only. Any app user can query everyone's friend graph, pending requests, inbox payloads.
- **B2 (CRITICAL)** Firebase RTDB: no Firebase Authentication, no security rules versioned or
  deployed-verifiable. Path scheme (`rooms/{roomID}/users/{userID}`) derivable from source.
- **B3 (CRITICAL)** No `PrivacyInfo.xcprivacy` despite HealthKit heart-rate collection.
- **B4 (HIGH)** Keychain ACL `.whenUnlocked` instead of `.whenUnlockedThisDeviceOnly`
  (`Core/Authentication/KeychainService.swift:15-44`).
- **B5 (HIGH)** Heart rate logged cleartext via OSLog on Watch (numeric interpolation is
  `.public` by default) — `WatchHeartRateManager.swift:157`.
- **B6 (clean)** No hardcoded secrets; Keychain correctly used; `GoogleService-Info.plist`
  gitignored; HealthKit usage descriptions complete; disciplined `Log.*` usage.

## C. Lifecycle & Concurrency

- **C1 (CRITICAL, ×4 auditors)** `RoomViewModel` is never torn down except by the explicit
  Leave button. No `.onDisappear`, no `deinit`; swipe-back not blocked. Reproducible: enter
  room → Settings → Sign Out ⇒ the 4 stored Tasks run forever, HR keeps being written to
  Firebase after sign-out, zombie `HKWorkoutSession` on the Watch.
  `Features/Rooms/ViewModels/RoomViewModel.swift:36-38,201-208`, `Views/RoomView.swift`.
- **C2 (CRITICAL)** `FirebaseRoomRepository.observeParticipants` never checks
  `Task.isCancelled` in its forwarding loop → Firebase listener never removed, even on clean
  exit (`FirebaseRoomRepository.swift:69-85`).
- **C3 (CRITICAL)** Real data races behind `@unchecked Sendable`: `WatchHeartRateManager`
  and `HealthKitHeartRateService.streamContinuation` mutated across MainActor and
  HealthKit/WCSession delegate queues. 13-14 classes use `@unchecked Sendable` with zero
  justification; `[String: Any]` (non-Sendable) is the universal cross-boundary payload.
- **C4 (HIGH)** `PhoneSessionManager.heartRateHandler` never cleared; mutable callbacks +
  4 singletons form a second, untestable communication channel bypassing the DI/protocols
  (protocol covers ~40 % of the surface actually used; downcasts in `RoomViewModel:178` and
  `FirebaseRoomRepository:42,53`).
- **C5 (HIGH)** `FirebaseTemporaryRoomRepository` one-shot reads via
  `withCheckedContinuation` + 5 s timeout Task — fragile by construction; the timeout does not
  actually unblock `AccountDeletionService` (hang risk). Add `read(path:)` to the protocol instead.
- **C6 (clean)** All ViewModels correctly `@MainActor`; `AccountDeletionService` ordering
  race-free; structured cancellation in `enterRoom`/`exitRoom` correct at VM level.

## D. Silent-failure philosophy

- **D1 (CRITICAL)** `FirebaseRoomRepository.init` falls back to `MockFirebaseService`
  **in release builds** when Firebase is unconfigured — app "works", room stays empty, no signal.
- **D2 (CRITICAL)** `FirebaseRealtimeService.observe` has no error path (`AsyncStream`, Firebase
  `withCancel` unused): permission denied ⇒ forever-empty room, indistinguishable from a
  genuinely empty one.
- **D3 (HIGH)** `try? result.get()` / bare `try?` swallow corrupted CloudKit records and inbox
  writes with zero logging; `InboxMessageType` has no `unknown` case (messages from newer app
  versions vanish); partial parse failures fabricate 0-BPM participants.
- **D4 (HIGH)** CloudKit: near-zero `CKError` handling (quota/network/conflict/auth);
  read-modify-write races on `Group.memberIDs` and friend-request acceptance without
  `serverRecordChanged` handling ⇒ silent member loss.
- **D5 (HIGH)** `AccountDeletionService`: 6 non-transactional steps; failure mid-way leaves
  inconsistent state with no resume path.

## E. Correctness bugs

- **E1 (probable bug)** Temp-room ID parsing: `exitRoom` splits the roomID with
  `split(separator: "_", maxSplits: 1)` but Apple IDs contain dots mangled to underscores by
  `firebaseSafe()` ⇒ truncated user IDs ⇒ orphaned temp-room index entries
  (`RoomViewModel.swift:236-244`). Root cause: `firebaseSafe()` mangling leaked into business logic.
- **E2 (HIGH)** Stale-capture race in the shared `.navigationDestination(isPresented:)` pattern
  (Inbox/Friends): a second accepted invite can silently overwrite the first. Same room can be
  entered from 4 tabs with no single source of truth.
- **E3 (process)** The uncommitted Feb-17 diff contains a *real* fix of the same family
  (`firebaseSafe()` ID comparison in `allParticipantsForPlot`) plus the Watch wake-up feature.

## F. Performance & Energy

- **F1 (CRITICAL, ×2 auditors)** `syncGraph` is an uncached computed property (adjacency +
  BFS + Bron-Kerbosch) read 3–15× per heartbeat tick from ~4 call sites.
- **F2 (CRITICAL)** Whole-room Firebase observation ⇒ full-array replacement ⇒ full-screen
  invalidation on any single participant write; `RoomParticipant`/`WatchParticipant` not
  `Equatable` ⇒ all ~20 markers re-render every tick.
- **F3 (CRITICAL)** `AnimatedBackground`: Timer + 15 Hz Canvas + `repeatForever` on all 5 tab
  roots (TabView keeps them alive ⇒ up to 5 concurrent instances). **Zero `scenePhase`
  handling app-wide.** Estimated 3–6 %/h extra drain.
- **F4 (HIGH)** Unbounded `SyncStar` spawning with per-instance blurred `repeatForever`
  animations; `.ultraThinMaterial` stacked over the never-stopping background (continuous GPU blur).
- **F5 (HIGH)** `ClusterCircleView` 2× O(members×participants) scans per cluster per render;
  BFS uses `Array.removeFirst()` (O(n) dequeue); sequential CloudKit fetches in
  `GroupDetailViewModel.fetchDetails()`.
- **F6 (HIGH)** Unused `remote-notification` / HealthKit background-delivery entitlements declared.

## G. UX & Accessibility

- **G1 (CRITICAL)** Sign-In: real `signInWithApple()` wired to a transparent overlay
  `.onTapGesture`; native `SignInWithAppleButton` has no-op closures ⇒ likely VoiceOver dead end
  at the app's only entry point (`SignInView.swift`).
- **G2 (HIGH)** `StatusBadge` white-on-pastel fails WCAG AA (~1.5:1 vs 4.5:1 required), 7 sites.
- **G3 (HIGH)** Zero Reduce Motion checks despite perpetual animations; `HeartPlotView` hides
  all per-participant sync data from VoiceOver; watchOS Room screen ~0 % VoiceOver coverage
  (iOS HUD equivalent is exemplary — use as template).
- **G4 (HIGH)** Destructive actions without confirmation: swipe-delete Group (the same action
  in `GroupDetailView` IS gated), Leave Group ×2, Remove Friend. HealthKit-denied alert has no
  "Open Settings" action (dead end on the core flow). No initial loading state on the 4 list views.
- **G5 (HIGH)** iPad declared (`TARGETED_DEVICE_FAMILY = "1,2"`) but zero adaptive code.
- **G6 (CRITICAL, structural)** No deep-link infrastructure and no cross-tab navigation
  coordinator (`selectedTab` is private `@State`).

## H. Architecture (structural)

- **H1** `WematchShared` framework is empty (10 lines) — pure cost (embed phases, historical
  platform-mismatch crash) while ~500 lines are duplicated between iPhone and Watch (Bezier math
  identical line-for-line, `Color+Hex`, participant models, message schema).
  Proper fix: local multiplatform Swift package (iOS + watchOS).
- **H2** `WatchMessage.swift` is dead code — a typed message factory with zero callers; the
  radio protocol is stringly-typed dictionaries defined implicitly in 4 places across 2 targets.
- **H3** `RoomViewModel` is a god object (440 lines: lifecycle, HR streaming, Firebase writes,
  sync detection, star simulation, Watch relay, temp-room GC).
- **H4** MVVM bypassed in exactly 2 views: `BrowseGroupsView` and `JoinGroupSheet`
  (direct `CloudKitGroupRepository()` + business logic in View).
- **H5** Two VM-creation patterns coexist (`@State vm: VM?` + `.task` vs non-optional in `init`);
  no composition root (concrete repos defaulted in VM inits — pragmatic, but blocks staging/prod split).
- **H6** `InboxMessageRepository` (writes) lives under `Features/Groups/`, reads under
  `Features/Inbox/` — two inbox repos, two folders.
- **H7 (Swift 6 landmine)** `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` will break the test
  target the moment it is wired in; mocks not `Sendable`; 4/6 test files share real OS Keychain
  state under one hardcoded key.

## I. What is genuinely good (preserve)

1. Repository layer is real: 6 domains, uniform protocols, no CKRecord/DatabaseReference ever
   reaches a ViewModel — this is what makes everything else repairable.
2. Fully modern state/concurrency at VM level: `@Observable` + `@MainActor` everywhere, zero
   Combine, zero `ObservableObject` legacy, structured tasks with clean cancellation.
3. `SyncGraph`: pure Sendable value type, pivoted Bron-Kerbosch + BFS — the scientific core is
   properly isolated from rendering (and is the #1 immediate unit-test candidate).
4. "Watch = passive display" decision: right battery/consistency trade-off; symmetric
   HealthKit workout lifecycle; Firebase presence auto-cleaned via `onDisconnectRemoveValue`.
5. Base hygiene: systematic os.Logger, no `print`, near-zero force unwraps, defensive CloudKit
   (schema bootstrap, no-OR-predicate workarounds, member-cap checked on both sides),
   exemplary accessibility on the RoomView HUD.
